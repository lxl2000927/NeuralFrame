# NeuralFrame 全项目审查

日期：2026-11-19  
对象：当前 0.1.2 开发工作区  
范围：React/Electron UI、交互与动画、组件下载/导入/选择/应用/恢复、程序性能，以及 DLSS5-Swapper Enhanced、RTX-FG-Manager 对照。

## 结论

当前版本的基础质量较好：本轮没有发现 P0 级安全问题、数据损坏问题或阻断主流程的功能故障。组件校验、应用前预览、二次校验、事务回滚、未知文件保护、减弱动画和真实游戏只读界面流程均已形成较完整的实现与测试。

下一版最值得优先处理的不是继续增加后端，而是两项可测的性能热点、后台运行检测策略，以及组件下载与缓存管理。

- **高优先级**：中文静态翻译的重复正则匹配；默认运行检测产生的 PowerShell 与扫描开销。
- **中优先级**：组件详情抽屉的焦点边界；GitHub 单来源、更新检查串行、主动取消不保留分段、缓存无清理入口。
- **体验改进**：窄窗口布局、字体缩放、下载队列和整体进度、每游戏配置预设。
- **验证边界**：本轮没有改写真实游戏，也没有把文件测试结果解释为游戏内画质、帧率或延迟已经验收。

## 已确认做得好的部分

### UI、交互与动画

- 页面切换、卡片、按钮和抽屉的动画时长主要控制在 120–220ms，没有长时间循环动效。
- `prefers-reduced-motion`、`prefers-reduced-transparency`、强制色彩和软件兼容模式均有处理；减弱动画会同步移除平滑滚动和过渡。
- 原生 `dialog`、自定义 Select 的方向键/Home/End/Typeahead、抽屉 Escape 与打开按钮焦点恢复均有实现。
- 真实 960px 截图未见整体横向溢出、按钮不可达或主题失效；主要问题是信息密度，而不是布局损坏。

### 组件完整链路

- 下载限制协议、来源、大小和响应边界；SHA-256 不匹配不会入库。
- 大文件使用有界分段并发；普通网络中断会保留分段，进程异常后的续传也有测试。
- ZIP 有路径穿越、符号链接、大小写冲突、文件数量和总大小限制。
- 导入按内容寻址去重，保留手动导入与受信任适配器的来源区别。
- 应用前展示新增/替换/保留；应用前重新检查快照和游戏状态；部署、配置和外部步骤采用事务及回滚。
- 文件扫描已移入 inspection worker，封面有本地缓存、解码缓存、并发限制、失败退避和 lazy loading。

## 问题与改进建议

### P1：中文静态文案有不必要的动态正则匹配

**证据**

- `ui/src/i18n.ts:51-75`：中文模式下，普通静态 key 经 `reverse` 查询后仍等于原文，于是继续遍历全部动态 pattern 和前缀规则。
- 当前词典有 2,311 条，其中 181 条动态 pattern。
- 本轮直接调用当前 `t("游戏")` 10,000 次：中文 **54.39ms**，英文 **1.59ms**。这是翻译函数微基准，不代表整个界面会快 34 倍，但说明中文路径存在明确额外开销。
- 游戏和组件列表会在每次 React 渲染中多次调用 `t()`，大列表会放大该成本。

**建议**

在动态 pattern 遍历前增加中文精确 key 的快速返回，例如确认 `current === "zh" && Object.hasOwn(catalog, source)` 时直接返回 `source`。保留后端动态中文消息的 pattern 回退，并补充静态中文、动态中文、英文和占位符顺序测试。

### P1：普通配置页的后台运行检测成本偏高

**证据**

- `ui/src/features/GraphicsPanels.tsx:47-64`：普通图形页默认每 10 秒调用 `component-runtime`。
- `ui/src/features/StandaloneStatus.tsx:57-73`：独立宿主默认每 5 秒检测。
- `src/core/runtime-status.js:178-201`：每 30 秒重新执行游戏扫描；进程查询通过 PowerShell。
- 对真实《ELDEN RING》目录只读测量：冷检测约 **3.1–3.6 秒**，缓存扫描后的检测约 **1.4 秒**；冷检测观测到约 **312ms** 主线程事件循环滞后。后一次检测的事件循环滞后约 12ms，主要耗时转为等待 PowerShell。

**影响**

页面停留期间会持续产生后台进程和 IPC 工作。后端 2.5 秒合并能避免同一时刻重复探测，但不能消除 5/10 秒定时器带来的周期性成本。

**建议**

1. 配置页只做首次检测和手动刷新；持续采样由“运行诊断”或用户显式开关启动。
2. 游戏未运行时采用 30–60 秒退避，运行中再提高到 5–10 秒。
3. 多个 UI 消费者共用一个按游戏调度的采样器，不各自维护定时器。
4. 将周期扫描复用 inspection worker；后续再考虑原生进程查询，避免频繁启动 PowerShell。

### P2：组件详情抽屉还不是完整的模态可访问性边界

**证据**

- `ui/src/features/LibraryComponents.tsx:236-242` 只将 `.library-page` 设为 `inert`。
- `ui/src/features/LibraryComponents.tsx:282-299` 使用 `aside`，没有 `role="dialog"`、`aria-modal="true"` 或焦点循环。
- 侧栏、标题栏和其他不在 `.library-page` 内的可聚焦元素没有同步 inert。

**建议**

将其明确为实现为模态抽屉：增加 dialog 语义、Tab/Shift+Tab 焦点循环、背景兄弟节点 inert；保留现有 Escape、关闭动画和焦点恢复。增加“从关闭按钮 Shift+Tab 不离开抽屉”和“最后一个控件 Tab 返回第一个控件”的 Electron 测试。

### P2：组件下载仍只有 GitHub 单一路线

**证据**

- `src/core/component-updates.js:285-337` 的版本检查固定访问 GitHub API。
- `src/core/github-download.js` 只允许 GitHub 发布及资源主机，没有镜像或备用来源。
- RTX-FG-Manager 提供 GitCode/GitHub 优先级和顺序故障切换，同时保留固定大小与哈希验证。

**建议**

增加“国内源优先 / GitHub 优先”和逐文件故障切换。备用源必须继续使用预期 SHA-256、大小、协议和重定向白名单，不能为了可用性降低校验。界面显示当前来源和切换原因。

### P2：版本检查串行且不可取消

**证据**

- `src/core/component-updates.js:290-337` 对 10 个仓库逐个等待，每个请求超时上限 30 秒。
- 慢网络下完整检查可能长时间停留在“检查中”；该阶段的 `cancel()` 不会取消这些请求。

**建议**

使用 2–3 个并发的小型调度器，保留共享限流闸门、ETag 和错误隔离；将检查也纳入统一 AbortController。网络差时先展示已有缓存，后台更新，不阻塞本地导入和已缓存组件。

### P2：主动取消与暂停的语义需要分开

**证据**

- `src/core/asset-download.js:193-205` 在显式 abort 时清理分段；注释和测试也明确了这一产品选择。
- 本轮大文件模拟证明普通断线会保留分段，因此问题仅限于用户主动取消，不是底层续传失效。
- 大组件可达数百 MiB，完整运行时包更大，误点取消后只能重新下载。

**建议**

提供“暂停并保留进度”和“取消并清理”两种动作；保留 24 小时清理策略，并显示将保留或删除多少数据。完整性校验和入库规则保持不变。

### P2：缺少组件缓存治理入口

**证据**

当前 UI/IPC 没有清理缓存或删除未使用版本的入口。组件库支持多版本和手动导入，长期使用后只能手工处理目录。RTX-FG-Manager 已提供“清理下载缓存但保留游戏列表、参数和备份”。

**建议**

增加缓存总大小、按组件占用、最后使用时间和未使用版本清理。默认保留当前选择、已部署所需版本和原始备份；清理只针对可重新下载的缓存，并提供预览和撤销到回收站的可选策略。

### P2：多文件任务还缺少整体进度和下载队列

**证据**

当前实现已经有单文件百分比、速度和部分流程的 ETA，准备组件时也能显示 `index/count`。但进度主要按当前文件计算，不能表达整个依赖集合的总字节和剩余任务；全局 busy 使用户不能先排队后续下载。

**建议**

参考 RTX-FG-Manager 的 `queue/file/aggregate/source/phase` 进度模型，增加整体完成量、当前文件 x/y、来源和阶段。下载允许有限排队，应用、卸载和恢复继续保持互斥，不能为了并行而放松事务边界。

### P3：窄窗口和长时间使用可继续优化

- 960px 没有功能性溢出，但游戏列表、详情、固定底栏同时存在，视觉密度较高；组件表的多列省略信息较多。
- 可借鉴 RTX-FG-Manager 的可折叠侧栏、可拖宽详情区、12–18px 字体调节。NeuralFrame 当前固定侧栏且只有明暗两套主题、中英文两种语言，不必照搬 38 套主题。
- 游戏列表当前一次性渲染全部筛选结果。普通规模没有问题；若目标是数百到上千游戏，可增加虚拟列表或分批渲染。
- `dateTime()` 可按语言缓存 `Intl.DateTimeFormat`，避免列表中重复创建 formatter。
- `artworkQueue` 完成任务长期保留在 Map 中，正常游戏规模有界；频繁增删游戏时可增加已完成任务淘汰。

## 两个上游项目对照

### DLSS5-Swapper Enhanced 2.3.3

NeuralFrame 已经吸收其主要有价值方向，不需要重复照搬：

- 硬件档位、笔记本省显存参数和自动档位来源：`HardwareProfileChoices` 与后端状态已覆盖。
- 显存估算及“估算不等于实测”的表达：`GameReports` 已覆盖。
- NR/MFG 独立配置、文件检查、恢复：现有实现更统一，并增加应用预览和组件来源证据。

可继续借鉴的是“常用操作更简单”：为普通用户提供推荐配置/快速模式，把高级选项留在现有完整页面；快速模式仍必须经过预览，不恢复成无差异的一键覆盖。上游 README 中的性能和兼容性声明仍需逐项实测，不能直接当作 NeuralFrame 的验收结论。

### RTX-FG-Manager 本地 2026-11-14 快照（README 标注 4.3.33）

最值得借鉴：

1. GitCode/GitHub 源切换与故障回退。
2. 下载总队列、当前文件、总进度、速度、连接数、来源和阶段。
3. 可折叠/可调布局、字体缩放、缓存清理。
4. 参数预设和分享协议，但先做**本地命名预设与安全导出**，不必直接引入社区服务。
5. 更细的运行清单、私有依赖配对和版本化参数协议；NeuralFrame 新组件已沿这个方向实现，应继续保持。

不建议直接照搬：

- 多游戏批量写入。若增加批量能力，优先做批量扫描、检查和导出；批量应用必须逐游戏预览、冲突隔离和独立回滚。
- 大量主题、语言或社区功能。当前优先级低于性能、下载可靠性和真实游戏验收。

## 推荐实施顺序

1. **小改动先落地**：中文精确 key 快速返回；运行检测改手动/退避；补对应性能和回归测试。
2. **补下载体验**：备用来源、可取消检查、暂停保留、整体进度和下载队列。
3. **补长期可用性**：缓存治理、抽屉完整焦点边界、折叠布局与字体缩放。
4. **再做效率功能**：本地配置预设、只读批量扫描/导出。
5. **发布前验收**：配置 Zig 后补齐 native bridge 测试，再做真实游戏画质、帧时间、1% Low、显存、延迟和实际输出倍率验证。
